# Design

## Context

`pictura_filters::Filter` has 112 variants. The engine's knowledge about each kind is currently held in seven variant-keyed matches across two crates, and each of the seven ends in a wildcard arm — a `_` in the five `match`es, a `_ => false` in the two `matches!`es:

```
pictura-filters                         pictura-render
  filter/apply.rs        match ... _ => Err(Unsupported)     39 native arms
  filter/types.rs        matches!(f, 44 names)               68 variants fall through
  photorust/dispatch.rs  plan          _ => plan_strokes()   30 arms
                         plan_strokes  _ => plan_sketch()    23 arms
                         plan_sketch   _ => return None      20 arms
  filter.rs              preview_apron   _ => 128.0          22 variants, 15 arms
                         cpu_outruns_gpu matches!(11 names)
```

The `_` in `matches!` is the reason the gap is invisible: `matches!(e, p)` expands to `match e { p => true, _ => false }`, so the fallback is always there and a new variant compiles with no decision. The seven matches are also not the only copies — the oracle mapping test asserts "one mapping row per Filter variant … full enum coverage" over a hand-typed list of 56 names, and `docs/GLOSSARY.md` names the alpha fact by function name.

Consumers are few: `filters_alpha` has four call sites (the ported engine's alpha write-back, the GPU plane count, the render crate's alpha test and the ported-engine contract test), `preview_apron` has three in the application (`impl_filters.rs` twice, `canvas_proxy.rs` once) and three in the render crate's own apron test, and `cpu_outruns_gpu` has two (the layer dispatch and the CPU-preferred test). Moving the facts is therefore a small blast radius; the cost is in writing them out.

## Goals / Non-Goals

**Goals:**

- Every per-variant fact is decided in one place, inside `pictura-filters`, and the compiler rejects a variant that has no decision.
- The facts are queryable (`filter.moves_alpha()`, `filter.preview_apron()`, `filter.cpu_outruns_gpu()`, `filter.engine()`), so the render crate and the application ask a filter instead of keeping a variant list.
- The coverage tests iterate a variant list generated from the type, so they cannot claim coverage they do not have.
- No filter's output, parameter or oracle changes.

**Non-Goals:**

- No new filter, no kernel work, no oracle research beyond recording which variants have an ImageMagick operator.
- The GPU kernel plan (`crates/pictura-render/src/gpu_filter/plan.rs`) keeps its own partial match: it is an eighth variant-keyed match, but it holds none of the four facts this change moves — the plan is parameter-dependent (Surface Blur's GPU plan stops at radius 16), so a per-variant boolean would be a lie. The kind-level GPU-eligibility fact is out of scope; a future GPU-eligibility query can read it.
- The application's kind-keyed tables (`cxxqt_object/filter_map.rs`, `filter_tools.rs::filter_preview_needs_whole_layer`) are untouched: they are keyed by the application's own kind strings and are single-sourced by #270.
- No new dependency.

## Decisions

**1. The facts are methods on the filter type, in a new module.** `crates/pictura-filters/src/filter/props.rs` holds them; `pictura-render` and the application call them. The alternative — keeping them in the render crate and making them exhaustive there — leaves the fact split across crates, which is the problem the issue names, and gives the engine crate no way to answer "does this filter move alpha?" for its own kernels.
   - *Alternative considered:* a free function per fact in `pictura-filters` (`pictura_filters::moves_alpha(&filter)`) — rejected: the call sites read as table lookups, and a method makes the "ask the filter" idiom the only one available.

**2. Exhaustiveness is a `match` with no wildcard arm; `matches!` is not usable for a fact.** This is the whole enforcement mechanism: a `match` over `FilterKind` that names every variant fails to compile when a variant is added and not named, while `matches!` always compiles. The kind-level fact tables therefore use `|` groups where several variants share a decision, but never a `_`; the value-level methods delegate to the kind-level match (Smart Blur's mode is the one value-dependent exception), so they do not restate the table.
   - *Alternative considered:* a derive macro that generates the facts — rejected: the facts are per-variant judgements, not a mechanical function of the variant's shape, and a derive would still need a per-variant table to read from.

**3. The variant list is generated by a macro, and the compiler rejects drift in both directions.** `crates/pictura-filters/src/filter/variants.rs` holds a `filter_variants!` invocation that lists each variant once with the engine that applies it, and expands to a `FilterKind` enum, `FilterKind::ALL`, `Filter::kind()`, `FilterKind::name()`, a `FilterEngine` enum (`Native`, `Ported`), `FilterKind::engine()` and `Filter::engine()`. The generated `kind()` match is exhaustive over `Filter`, so a variant missing from the list is a non-exhaustive-pattern error and a name in the list that is not a variant is a no-such-variant error. The list can never drift silently.
   - The table carries each variant's *pattern shape* as well as its name, because `Filter` has three shapes and one pattern does not fit all of them: 99 variants carry named fields (`Filter::GaussianBlur { .. }`), two are tuple variants (`Filter::ReduceNoise(..)`, `Filter::HdrToning(..)`) and eleven are unit variants (`Filter::Average`, `Filter::Solarize`, …). `Filter::ReduceNoise { .. }` is a compile error — a tuple variant cannot be written as a struct variant — so the macro has three rules, one per shape, and every generated and hand-written match over `Filter` uses the shape's own pattern.
   - *Alternative considered:* `strum`'s `EnumDiscriminants` / `EnumIter` derive — rejected: a new dependency for one enum, and the derive's list carries no name-to-row lookup that the coverage test needs.
   - *Alternative considered:* a macro that *defines* the enum, so the list is the definition — rejected: the enum's variants carry doc comments and three different shapes (named fields, the tuple variants `ReduceNoise` and `HdrToning`, and the unit variants), so a macro that owned the definition would have to encode all of them and would move the enum's documentation into macro arguments. The macro that lists the names beside their engine leaves the enum readable and touches nothing but the new module.
   - *Alternative considered:* a hand-written name list plus a hand-written `kind()` match — rejected: two hand-maintained copies of the same 112 names, which is the class of duplication this change exists to remove.

**4. Facts that do not depend on a variant's parameters are decided on the kind; facts that do are decided on the value.** `engine` (carried by the generated list), `cpu_outruns_gpu` and the moving-alpha *set* are kind-level: one decision per variant, exhaustive over the generated list, and therefore runtime-testable for all 112 variants at once. `preview_apron` and the moving-alpha *behaviour* are value-level, because the apron depends on the radius and Smart Blur moves the alpha plane in Normal mode only.
   - The moving-alpha fact is therefore two decisions with one exception between them: `FilterKind::moves_alpha()` states which variants move (Smart Blur counts as moving), and `Filter::moves_alpha()` delegates to it except for Smart Blur, which checks its mode. The render crate's moving-kernel fixture is compared against the kind-level set, so the two cannot drift without a failing test.
   - *Alternative considered:* one value-level table for the alpha fact — rejected: the render fixture's completeness (does the fixture hold one instance of every moving variant?) is then not checkable at run time, because deciding "does this kind move" needs a kind, and the fixture is a list of values whose kinds must be compared against a set.
   - The change needs a list of one default instance per variant to test the facts against: the `pictura-filters` crate's own tests already build instances for 104 of the 112 variants (`ported.rs`, `kernel_digests.rs` and `profile.rs`), and the eight it has none of are `Displace`, `Liquify`, `Glass`, `DiffuseGlow`, `DifferenceClouds`, `Lighting`, `SmartSharpen` and `HdrToning`. The change assembles the list in one shared `tests/common/` module rather than scattering it further.

**5. The engine partition is stated three times, in one crate, and the compiler checks completeness of all three.** The macro table is the partition; `filter/apply.rs` holds the native implementation; `photorust/dispatch.rs` holds the ported implementation. Each names every variant — the two implementation matches carry a grouped arm for the variants the other engine owns — so a variant neither implementation names is a non-exhaustive-pattern error, not a runtime gap.
   - `apply` routes on `Filter::engine()`: the property decides which engine is asked; the native match refuses a variant it does not implement with `FilterError::Unsupported`, and the ported dispatch's `None` ("not a ported variant") becomes the same error when the property routed the variant there. Without that routing a misplacement would silently run the *other* engine's kernel (today `apply` tries the ported engine first and falls back to the native match), which is the outcome the requirement forbids.
   - *Alternative considered:* two lists — the routing match in `apply.rs` doubles as the classification, with no queryable property. Rejected: a future GPU-eligibility query is expected to read an engine fact, and the issue asks for the dispatch to be a property of the filter.
   - *Alternative considered:* a macro that owns the enum and generates both the partition and the implementations — rejected: macro hygiene puts a per-variant kernel body at the call site's hygiene context, where it cannot see the fields the macro binds, so the bodies cannot be written inside the table.
   - *Alternative considered:* a sub-enum per engine carrying the variant's parameters (`NativeOp`, `PhotorustOp`) so each implementation matches over its own narrow enum — rejected: `Filter` holds `Vec` and `Arc` payloads, so the sub-enum would have to clone or re-borrow them, and the lifetime plumbing costs more than the duplication it removes.

**6. The ported dispatch collapses from a chain of three functions into one match.** `plan` → `plan_strokes` → `plan_sketch` cannot be made exhaustive as a chain: the compiler checks one match at a time, so making the last function exhaustive would require it to name the variants the earlier functions already handle. One match over all 112 variants is the only shape the compiler can check. The three functions' bodies merge into that match; the per-family bodies stay in the existing `photorust::{brush_strokes,sketch,texture}` modules. The 39 variants the native engine owns get one grouped arm that returns `None` ("not a ported variant"), and the file stays at roughly its current size — 1103 lines today, above the 800-line target and under the 1200-line cap, so the allowlist needs no new entry.
   - *Alternative considered:* keep the chain and make each function's fallback an explicit group — rejected: the compiler then checks each function's own variants, not the union, so a variant added to the first function's group and missing from the second's would compile.

**7. `filters_alpha` becomes `Filter::moves_alpha()`, and the render crate's two tables are deleted.** `pictura_filters::filters_alpha` and `pictura_render::preview_apron` are removed from the crates' public surfaces; `pictura_render`'s `preview_apron` re-export goes with them, and the three application call sites call the property. The render crate's crate-private `cpu_outruns_gpu` moves to the property with its two call sites — the layer dispatch and the CPU-preferred test — keeping its `ponytail:` note about the one-machine crossover, because the note travels because the measurement travels. `preview_apron` brings its private `path_reach` helper along; it reads only `BlurPath` and `PathMotion` fields.
   - *Alternative considered:* leave `cpu_outruns_gpu` in the render crate and make it exhaustive there — rejected: the fact would then live in a different crate from the other three, and the issue asks for one place. The cost is that the Qt-free engine crate now names a GPU policy; the `ponytail:` comment marks it as a measurement to re-take on other hardware.

**8. The coverage tests gain a per-variant decision.** The oracle mapping table grows from 56 rows to one row per variant: each row names the ImageMagick operator that is the variant's oracle, or names none and states why it has none. The digest test records a digest for every variant whose kernel runs row-parallel and records explicitly that the others have none. The ported contract test is checked against the generated list's ported entries. Each iterates the generated list, so an undecided variant fails the test.
   - The hand-written coverage lists the tests carry today go with them: `mapping_marks_no_equivalent_operators` asserts `MAPPING.len() == 56`, compares against a typed 56-name `all` list, and compares the no-equivalent rows against `NO_EQUIVALENT`; `ported.rs`'s `cases()` holds 71 of the 73 ported variants (`Displace` and `Shear` are missing). The new per-variant checks replace the mapping lists (the row's note carries the no-equivalent reason), and the ported check fails until the two missing cases are written.
   - *Alternative considered:* leave the mapping table at 56 rows and add a note that the artistic filters have no oracle — rejected: the table is the coverage claim, and a table that covers half the enum while claiming to cover all of it is the defect the issue names.

## Risks / Trade-offs

- [The engine partition is stated three times] → the compiler rejects an omission in any of the three; a *disagreement* between them degrades to `FilterError::Unsupported`, never a wrong kernel, because `apply` routes on the property and the engine it is routed to refuses a variant it does not implement. The new test `each_variant_is_applied_by_the_engine_its_property_names` applies every variant and fails on that refusal, so a misplacement that still compiles shows up there.
- [The generated list is a second statement of the variant names] → the generated `kind()` match is exhaustive over `Filter`, so drift in either direction is a compile error; the list cannot go stale.
- [The moving-alpha fact is a kind-level set plus a value-level exception] → the exception is one arm (`SmartBlur`'s mode); the render fixture is compared against the set, so the two diverge loudly.
- [Fifty-six new mapping rows need real research] → each row either names an operator from `magick -list filter` or states that there is none and why; the test requires the row to exist and its note to be non-empty, not that a new oracle is found.
- [The public API of `pictura-filters` changes] → the crate is workspace-internal; the render crate, the application and the engine's own tests move in the same change, and `docs/GLOSSARY.md` names the old symbol in a separate docs commit carrying `TASK-ALLOWS-DOCS`.
- [A large mechanical diff] → the facts are four 112-entry tables (the macro table, `FilterKind::moves_alpha()`, `Filter::preview_apron()` and `FilterKind::cpu_outruns_gpu()`), two generated 112-arm matches (`Filter::kind()` and `FilterKind::engine()`) and the two implementation matches. The compiler is the reviewer's checklist here: a wrong arm is a behaviour change, not a silent addition, and the existing filter tests cover the arms that matter.

## Migration Plan

None. The change is source-only: no persisted state, no file format, no user-visible behaviour. Rolling it back is a revert.

## Open Questions

None. The remaining choices (the `dispatch.rs` split, the application's kind tables) are either settled by the size cap and by #270, or do not change the specs, the approach, or the task breakdown.
