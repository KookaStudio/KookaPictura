# Design

## Context

`pictura::loadSession` and `saveSession` currently serve both the frame and smaller callers that patch one field at a time. The frame reloads the JSON and then overlays its in-memory values before saving. `settings_backup.cpp` bypasses the session save path and applies staged imports before frame construction. The JSON writer token rejects stale session saves and suppresses the corresponding workspace snapshot. An idle process has no presence in that check.

## Goals / Non-Goals

Keep typed defaults and validation close to the Rust store, preserve the app's existing preference timing, and make each legacy key's destination explicit. Keep the existing controls, shortcut override model, and workspace format as the scope of integration.

## Decisions

### Rust owns preference values and files

Add a Qt-free `prefs` module within `pictura-app` and a dedicated cxx-qt bridge. The preferences model uses typed structs and enums, with a TOML table retaining unrecognized values. Decode known fields through the same validator for disk loads, migrated input, direct edits, and imported preferences. Keep user overrides sparse so a newly seeded profile can still inherit changes to system defaults. Missing fields inherit, out-of-range numeric values use the corresponding existing normalization, and structurally invalid known values report validation failure. Check `schema_version` before typed decoding so an unfamiliar schema is read-only even when a known field changed shape. Preserve the existing IDs for shortcut overrides and use portable binding strings as today.

Use `toml` with `serde` because the store needs a standard parser and serializer and must round-trip values that JSON cannot represent directly. A generic JSON value map would leave type validation to individual consumers. A Qt settings writer would give the shell ownership of the file, and a separate Rust crate would add a package boundary for a store whose callers all live in the app.

Resolve roots at startup and use the same profile paths throughout startup, writes, import, and reset. On Linux, resolve absolute XDG overrides and the standard config fallback. Treat system files as read-only defaults in XDG directory precedence order. Delegate the non-XDG config base to the shell's platform path helper before appending the product directory. Keep resolving legacy state from the current session location. For `--state-home DIR`, pass `DIR/config` as the user config base so existing automation can isolate the whole profile with one flag. Give self-test precedence over both environment and CLI overrides. Make Qt fixtures scope and restore both overrides, including preset tests that nest fixtures.

### Give each persisted field one owner

| Store | Existing data |
|---|---|
| TOML | Interface theme, brightness and scale, document opening and zoom behavior, tool switching, update opt-in, picker choice, Type, Performance, File Handling and Camera Raw storage choice, Units & Rulers defaults, guide style, remembered dialog suppression, agent preference controls, Color Settings, and command and tool shortcut overrides. |
| Session JSON | Opaque layout, window geometry and maximization, panel groups, columns, and the Tools column shape, recent files, current view toggles, tool options and Quick Mask options, panel-specific options and selections, last-used export, PDF and batch options, and any remaining legacy swatch fallback. |
| Workspace JSON | Existing named layouts, ordering and active workspace. |

Use an explicit mapping for migrated keys and name their destination by pane or feature. Keep `SessionState` focused on session data, and move consumers of migrated fields to a preferences snapshot or a field-specific path. Use the persisted value as each consumer's startup baseline. For edits, submit changed fields or shortcut entries explicitly. A stale frame's snapshot or a state-only update such as adding a recent file must not re-submit old preference values. Preserve the existing state writer protection and distinguish a state refusal from a preference failure so the workspace snapshot follows the state save result.

### Use a durable write and migration order

Serialize preference writes under a short-lived lock. Reload the current validated user table while holding the lock, apply the patch, and keep the latest unrelated and unknown keys. A conflicting field takes the latest committed edit. Use same-directory private temporary files and atomic replacement. Sync the file before publishing and sync the directory on Linux. Keep one last validated copy and compare the logical values to avoid no-op rewrites. A failed write or an unavailable lock keeps changes in memory and reports the failure. An application-wide last-writer-wins snapshot would lose disjoint edits. The pinned Rust toolchain provides file locks. See [Rust file locking](https://doc.rust-lang.org/std/fs/struct.File.html#method.try_lock_shared).

Read legacy JSON using the existing size bound and parsing rules. Extract the explicit map of known, present keys and apply legacy normalization. Publish and sync TOML before atomically rewriting the JSON to remove migrated keys and set a completion marker. A valid TOML document remains authoritative during cleanup retries. Keep the completion marker outside the user TOML so deleting that file after migration seeds defaults. Read a legacy snapshot into memory if its TOML write fails. Keep migrated keys and unknown JSON keys available until their respective store has successfully committed. Report quarantines once per recovery incident, preserve the invalid bytes before replacing the active file, and avoid rotating a malformed file into `.bak`. Never recover agent enablement, access level, approval mode, or allowed folders from a backup: force agent control off and its grants to restrictive defaults even over system defaults, persist that safe state and a local recovery guard in the recovered document, and require a fresh explicit user grant. While guarded, preference imports and their retries apply ordinary values but cannot restore agent opt-in or grants; preserve the guard across v1 patches and v2 replacements, omit it from portable exports, and clear it only as part of an explicit user grant under the preference write lock. If recovery cannot be persisted, keep the safe state and guard in memory, do not apply an import that could persist agent access, and repeat recovery on later attempts. A missing file after completed migration is an intentional absence and never automatically falls back to `.bak`.

### Apply reset and import before constructing the frame

Sample the startup gesture after Qt setup on platforms that expose it and use the explicit flag on Wayland. Both enter the same Qt confirmation before any stored settings are applied. Exclude self-test, headless and control-mode startup from the interactive dialog. Use shared presence locks for normal launches in both profile roots and exclusive locks for reset, acquired in a stable order. Hold the locks outside folders reset can move, and keep their handles alive for the relevant phase. The existing writer-token check only protects session saves and cannot replace these presence locks. Before any reset publication, durably register the transaction and both canonical roots in a discoverable recovery record at each root while holding both exclusive locks; publish nothing until both records are durable. A launch sharing either root checks its record before loading any affected settings, takes exclusive locks on both recorded roots in stable order, rechecks and completes recovery, and only then enters normal shared-presence mode. Recheck for records after acquiring normal shared locks; if one appears, release shared locks and perform exclusive recovery before loading. Clear both records only after recovery or commit is durable. An incomplete registration with no publication is discarded under both exclusive locks; an inaccessible root or ambiguous transaction blocks affected startup safely rather than allowing a partial profile to load. This also serializes concurrent recovery attempts.

Prepare private backups of preferences and their last-good file, named workspaces, and the session data being cleared. Move any pending import to the reset backup as part of the operation and identify it in the confirmation when one exists. Keep recovery and preset paths outside the reset targets. Stage each replacement beside its destination. Prepare everything before publishing, record the affected paths and transaction state, and retain original copies until the reset commits. Roll back a failed publication and recover an interrupted operation before applying stored settings on the next launch. This sequencing handles configuration and state on separate volumes. Load the factory dock layout after a successful reset while keeping window geometry and recents. Carry any active local agent recovery guard and restrictive agent overrides through reset; only a fresh explicit user grant clears the guard. Cancellation continues normal startup, including any independently staged import.

For a normal launch, recover or migrate the preferences before applying the pending import, then load the profile for the frame. Carry TOML as a string in the existing JSON backup envelope to preserve unknown value types. A version 2 import validates the preference payload before staging and replaces user overrides when that section is present. A version 1 import translates present legacy keys into a patch even on an already-migrated profile, stripping those keys from the imported session object. Preserve the local completion marker when replacing session JSON. Give each staged import a unique durable identity. Before applying an older pending v1 file lacking an identity, atomically assign and sync one in that pending file; if this fails, do not apply it. Atomically commit the identity in a reserved local receipt set in the same preference document replacement as the v1 patch or v2 replacement. Preserve all outstanding receipts across ordinary edits and other imports, including v2 replacements, since distinct state roots can share one config root. Omit receipts from portable exports. On retry, a matching receipt skips preference application while remaining sections and pending-file retirement retry, preserving intervening preference edits. Receipt checking, publication, and identity-specific cleanup share the preference write lock. Remove only that identity after its pending file is durably retired; a different pending identity is applied normally, and interrupted receipt cleanup is harmless. Keep pending data available after a failed commit. Use the same preference validation and write path for direct edits and imports.

The config root is a hard-denied agent file target alongside state and endpoint roots for both restricted live and CLI control, using canonical paths even when the roots differ.

## Risks / Trade-offs

- A frame can still carry older in-memory values after another process edits a preference. Field-level patches preserve the other process's unrelated edits at write time. A fresh launch reads the merged result.
- Some existing tests seed mixed JSON directly and others share an isolated profile. Keep legacy fixtures for migration coverage, update current-format fixtures to write to the owning store, and exercise both stores with temporary roots.
- Early-held modifier state depends on the platform. The flag exercises the full reset path in automated tests. A desktop check covers the physical startup chord. See [Qt Wayland modifier handling](https://codebrowser.dev/qt6/qtbase/src/plugins/platforms/wayland/qwaylandintegration.cpp.html#270).

## Migration Plan

Read pre-upgrade session files and version 1 backup files on the first release. Commit the new profile format per the migration order above. A user returning to an older executable can restore preferences using a version 1 backup made before upgrade. Version 2 backups can be restored on this release or a newer compatible one.
