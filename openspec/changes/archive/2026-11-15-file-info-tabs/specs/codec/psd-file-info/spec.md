# Spec Delta

## RENAMED Requirements

- FROM: `### Requirement: The application edits IPTC core fields in File Info`
- TO: `### Requirement: The application presents and edits File Info metadata`

## MODIFIED Requirements

### Requirement: The XMP packet is exposed as raw text

`read_metadata` SHALL expose the document's XMP image resource (id 1060) as a
UTF-8 (lossy) string, without resolving XML entities, so XXE and entity-expansion
payloads have no effect. `pictura-codec` SHALL additionally expose the packet's
typed managed properties (title, creator, description, subject, rights, credit,
source, headline, marked, city, state, country, instructions, authors position,
caption writer, web statement, and usage terms) parsed from the same resource,
per `psd-xmp-metadata`. The raw string is unchanged by the addition.

#### Scenario: The fixture's XMP packet is returned as text

- **WHEN** `read_metadata` reads the fixture
- **THEN** its XMP string equals the stored resource 1060 bytes decoded as text

#### Scenario: The parsed properties accompany the raw string

- **WHEN** the fixture's XMP is read
- **THEN** the parsed title, creator, description, rights, city, and usage terms are available alongside the raw string

### Requirement: The metadata fixture is proven by an independent decoder

The system SHALL commit the fixture
`crates/pictura-codec/tests/fixtures/metadata.psd`, regenerated byte-stably by
`scripts/generate-fixtures.py`, carrying a real EXIF IFD with a GPS sub-IFD, an
IPTC-IIM block with Origin and Keywords records, and an XMP packet with the
Description, Origin, IPTC Extension, and Photoshop properties, and a test SHALL
verify that `read_metadata`'s decoded EXIF, GPS, IPTC, and extension values agree
with the independent `exiftool` decoder for the same file. The oracle SHALL
self-skip with a clear message when `exiftool` is unavailable and SHALL NOT fail
the suite in that case.

#### Scenario: read_metadata agrees with exiftool

- **WHEN** `read_metadata` decodes `metadata.psd` and `exiftool` decodes the same file
- **THEN** the decoded Make, Model, Software, ExposureTime, FNumber, ISO, DateTimeOriginal, FocalLength, GPS latitude and longitude, and the IPTC Object Name, By-line, Copyright Notice, Caption-Abstract, City, and Keywords match

#### Scenario: The fixture's extension fields agree with exiftool

- **WHEN** the fixture's XMP is read and `exiftool` reads the same XMP
- **THEN** the person shown, event, location city, and rights usage terms match, and the engine-side image rating is 4

#### Scenario: The oracle self-skips without exiftool

- **WHEN** the `exiftool` binary is not available
- **THEN** the oracle reports a skip and the suite passes

### Requirement: The application presents and edits File Info metadata

The application SHALL enable `File > File Info…` when a document is open and
SHALL open a dialog listing the metadata under the categories Description,
Camera Data, IPTC, IPTC Extension, GPS Data, Origin, Photoshop, and Raw Data.
Video Data, Audio Data, and DICOM categories SHALL NOT be shown, because the
project has no video/audio layer kind or DICOM import and records them as not
planned.

The Description category SHALL present Document Title, Author, Author Title,
Description, Description Writer, Keywords, Copyright Status, Copyright Notice,
and Copyright Info URL as editable fields prefilled from the active document.
Copyright Status SHALL offer Unknown, Copyrighted, and Public Domain: Unknown
SHALL leave the rights-marked property absent, Copyrighted SHALL set it true,
and Public Domain SHALL set it false.

The Camera Data and GPS Data categories SHALL list the decoded EXIF and GPS
values read-only. The Photoshop category SHALL list the document's `photoshop:`,
`xmp:`, and `xmpMM:` properties read-only.

The IPTC category SHALL present Object Name, By-line, Copyright Notice,
Caption/Abstract, Credit, and Source as editable fields plus a read-only list of
the remaining IIM records. The Origin category SHALL present City,
State/Province, Country, Headline, Credit, Source, and Instructions as editable
fields. The IPTC Extension category SHALL present the supported extension fields
from `iptc-extension` as editable controls prefilled from the document, plus
Rights Usage Terms (`xmpRights:UsageTerms`) from the managed XMP set and a
read-only list of the remaining extension leaves. Every supported editable field
SHALL have a control even when the document has no value for it, so the user can
add the property.

Editing a field that maps to a shared IIM/XMP property in any category SHALL
update the same underlying value, so two categories that show the same property
never hold different values.

The Raw Data category SHALL present the XMP packet in an editable text area. On
OK an edited packet SHALL replace image resource 1060 only when it is
well-formed; an ill-formed packet SHALL apply nothing and keep the dialog open.

On OK the application SHALL apply only the fields the user changed (so an
untouched value is never rewritten), write each changed shared field to both the
XMP packet and the IIM record so the two never conflict, write each changed
XMP-only or extension field to the XMP packet, record exactly one undo state
labelled for the edit, and mark the document dirty; OK with no changed fields
SHALL apply nothing and record no state; on Cancel it SHALL apply nothing. A raw
packet edit SHALL be applied before the field edits, and the whole accept SHALL
remain one undo state.

The bridge SHALL expose read-only rows as `"Section\tLabel\tValue"`, editable
rows as `"Section\tid\tLabel\tValue"`, the raw packet, and an apply method taking
`"id\tValue"` rows and the raw packet row.

#### Scenario: File Info is disabled without a document

- **WHEN** no document is open
- **THEN** the `File > File Info…` command is disabled

#### Scenario: Opening File Info shows the editable categories

- **WHEN** the metadata fixture is open and `File > File Info…` is invoked
- **THEN** the dialog shows the Description, Camera Data, IPTC, IPTC Extension, GPS Data, Origin, Photoshop, and Raw Data categories; Camera Data lists the EXIF Make and GPS Data lists the decoded latitude; and no Video Data, Audio Data, or DICOM category exists

#### Scenario: Editing a field and accepting applies one undo state

- **WHEN** the Author field is changed and the dialog is accepted
- **THEN** the document's parsed XMP creator and IIM By-line are both the new value, the document is dirty, and one Undo restores both

#### Scenario: Editing an Origin field writes both channels

- **WHEN** the City field is changed and the dialog is accepted
- **THEN** the document's decoded IIM City and parsed XMP city are both the new value

#### Scenario: Editing an IPTC Extension field writes XMP only

- **WHEN** a person is added to Person Shown and the dialog is accepted
- **THEN** the packet carries the new bag item, the IIM resource is unchanged, and one Undo restores the previous extension state

#### Scenario: A shared field is mirrored across categories

- **WHEN** Object Name is changed in the IPTC category
- **THEN** the Description category's Document Title field holds the same text before the dialog is accepted

#### Scenario: Editing Raw Data and a field is one undo state

- **WHEN** the raw packet and a Description field are both changed and the dialog is accepted
- **THEN** the document carries both edits, exactly one undo state was added, and one Undo restores both

#### Scenario: An ill-formed raw packet applies nothing

- **WHEN** the Raw Data text is not well-formed and the dialog is accepted
- **THEN** no edit is applied, no undo state is recorded, and the dialog remains open

#### Scenario: A missing value still shows an editable control

- **WHEN** a supported field has no value in the document and File Info is opened
- **THEN** the field's control is present and empty so it can be filled in

#### Scenario: An unwritable extension field is refused and reported

- **WHEN** a requested extension field uses a packet shape the writer cannot safely rewrite and the dialog is accepted
- **THEN** the XMP resource is unchanged, no undo state is recorded for that group, and the dialog remains open

#### Scenario: Cancelling applies nothing

- **WHEN** any field is changed and the dialog is rejected
- **THEN** the document's metadata is unchanged and the document is not dirtied by the dialog

#### Scenario: Accepting with no changes records nothing

- **WHEN** the dialog is accepted without changing any field or the raw packet
- **THEN** no edit is applied, no undo state is recorded, and the document is not dirtied by the dialog
