# Design

## Context

See `proposal.md` — Why. Current state that shapes the approach:

- The top-level `CMakeLists.txt` finds Qt through `qmake6` and, for the RHI
  headers, hard-codes `"${QT_HEADERS_DIR}/QtGui/${QT_VERSION_STR}/QtGui"`
  (`CMakeLists.txt:59-64,417`). That resolves only on the Debian-style layout.
- CI provisions Qt with `jurplel/install-qt-action` (official Qt 6.11.1), which
  ships private headers and the `Qt6GuiPrivate` CMake package on Linux, macOS
  frameworks, and Windows. The official **macOS** Qt is built without Vulkan,
  so `QtGui/QVulkanInstance` is not shipped there, though `interop.cpp`
  includes it unconditionally outside its `QT_CONFIG(vulkan)` body guard.
- `macos.yml:43` runs the mac job only on the release-please PR, so a
  macOS-only build error cannot surface on a feature PR.
- The shell builds menus on `QMainWindow::menuBar()`. No call site sets
  `Qt::AA_DontUseNativeMenuBar` or `setNativeMenuBar(false)`, so macOS already
  gets the native bar; the shell's menu-bar styling and the workspace-frame
  offset assume an in-window bar and are unverified on macOS.

## Goals / Non-Goals

**Goals:**

- One cross-platform way to resolve the RHI/private include directory.
- The macOS release build compiles and links in CI.
- The native-menu-bar behaviour is stated as a contract and checked on the
  macOS runner.

**Non-Goals:**

- Making the macOS build run on every feature PR permanently (deliberately
  temporary here; the equivalent `appimage.yml:40` gate is a separate
  follow-up).
- Changing the menu structure, the About/Preferences/Quit entries, or their
  roles.
- Theming the native macOS menu bar (Qt does not style it).

## Decisions

### Resolve RHI headers through `Qt6::GuiPrivate`

Add `GuiPrivate` to the Qt component lookup and link `Qt6::GuiPrivate`
(PRIVATE, since only `interop.cpp` includes `<rhi/qrhi.h>`), then delete the
`qmake6 -query` header/version block and the hand-built include directory.
`QMAKE_EXECUTABLE` stays because `cxx_qt_import_crate` still needs it.

- **Why:** It is the mechanism Qt documents for this header (the "Simple RHI
  Widget" example links `Qt6::GuiPrivate` for exactly `#include <rhi/qrhi.h>`),
  and its include list is generated by Qt for each install layout. The existing
  path is a manual copy of what the target already exports on Linux.
- **Alternatives considered:** Per-platform fallback (`#if APPLE` framework
  path) — rejected, more code, still layout-fragile, and misses Windows.
  Keeping `qmake -query` and adding the macOS derivative — rejected, same
  fragility.
- **Require, don't fall back:** a missing private module fails configuration
  with a clear error instead of compiling an unresolved include. Distro-Qt
  developers need `qt6-base-private-dev`; CI already has the headers.

### Temporary PR gate, reverted after the fix

Drop the release-please-only `if:` at `macos.yml:43` and add the C++ source and
macOS packaging paths to its `paths:` list, so the fix is built on this PR. Both
edits carry a `ponytail:` comment naming the ceiling and are reverted within this
change once the macOS job is green on the PR; `.github/workflows/macos.yml` has
no net diff against `master`.

- **Why the user asked for temporary:** the mac runner is expensive; the
  permanent policy (drive the mac job from build-path PRs, and the same for
  appimage) is a separate decision.
- **Consequence:** this change does not, by itself, prevent the same
  feature-CI blind spot recurring; the follow-up is named in `proposal.md`.

### Verify the native bar with a platform-conditional check

A Qt Test asserts `QMainWindow::menuBar()->isNativeMenuBar()` reports the
platform-appropriate value (true on macOS, false elsewhere) and that it stays
true across screen modes. If the offscreen QPA plugin on the macOS runner makes
`isNativeMenuBar()` unreliable, the check degrades to a documented manual
macOS step; the decision is recorded in the task.

- **Why:** it is the only observable the shell controls; QSS/geometry
  assertions on an out-of-process native bar are not portable.
- **Not asserted:** the exact Application Menu contents — Qt merges by
  `QAction::menuRole()` and the outcome is a platform detail, not shell
  behaviour.
- **macOS runner outcome (task 3.2):** the macOS job builds the bundle with
  `BUILD_TESTING=OFF` and the smoke check runs `--headless` (offscreen), where
  `isNativeMenuBar()` is false on every platform — so the Qt Test would pass
  vacuously and cannot observe the cocoa menu bar. The automated macOS run is
  therefore not wired; the macOS verification is the documented manual step
  below.
- **Manual macOS verification (to run on a real macOS desktop session):**
  launch the built `pictura.app` normally (not `--headless`), confirm the menus
  appear in the system-wide bar at the top of the screen and not inside the
  window, and confirm About/Preferences/Quit are merged into the Application
  Menu. The app never sets `AA_DontUseNativeMenuBar` or `setNativeMenuBar`, so
  Qt's default (native on macOS) is in effect; the Linux `tst_native_menu_bar`
  locks in that no opt-out is introduced.

### Guard the Vulkan-only includes in `interop.cpp`

Move `<QtGui/qtguiglobal.h>` above the includes and wrap `<rhi/qrhi.h>` and
`<QtGui/QVulkanInstance>` in the same `#if QT_CONFIG(vulkan) &&
__has_include(<vulkan/vulkan.h>)` condition the probe body already uses.

- **Why:** the body was already a no-op stub when Vulkan is absent, but the
  unconditional include still failed to compile once the include path resolved
  on the macOS Qt (no Vulkan). Guarding the includes matches the body's
  contract and keeps the diagnostic probe a stub everywhere Qt lacks Vulkan.
- **This is a source change**, beyond the issue's "keep the fix build-only"
  direction, which was written before the macOS log showed the second error.
  It is minimal and confined to `interop.cpp`.

### Bundle the offscreen plugin for the headless smoke check

Copy `$QT_ROOT_DIR/plugins/platforms/libqoffscreen.dylib` into
`pictura.app/Contents/PlugIns/platforms/` before running `macdeployqt`, so the
single deploy run rewrites the plugin's framework references to the bundle.

- **Why:** `macos.yml` runs `pictura --headless --self-test` on the deployed
  bundle with the runner's Qt plugin path unset. `macdeployqt` deploys only the
  cocoa platform plugin, so `--headless` (offscreen) aborted. `linux-bundle`
  already sets `EXTRA_PLATFORM_PLUGINS: libqoffscreen.so` and `windows-bundle`
  copies `qoffscreen.dll` explicitly; macOS was the only platform without it,
  because its build never got this far.
- **Alternative considered:** drop `--headless` and run the self-test under
  cocoa — rejected; the runner may have no window server and the point is a
  self-contained bundle. Qt 6's `macdeployqt` has no `-extra-plugins`
  (Linux-only/older), so a manual copy is the documented mechanism.

### Guard the GPU probes against wgpu's no-backend panic

Early-return `None` from `pictura-render`'s `request_device()` and
`pictura-app`'s `gpu.rs::create_device()` when
`wgpu::Instance::enabled_backend_features()` does not include the Vulkan
backend, before `wgpu::Instance::new`.

- **Why:** `Instance::new` panics when no compiled-in backend is implemented for
  the target (Apple implements no Vulkan, and the workspace enables only the
  `vulkan` feature), and that panic crosses the cxx-qt FFI guard and aborts the
  process. The repository already accepts "no wgpu Vulkan backend on Apple
  targets" (`pictura-app/Cargo.toml` cfg-gates `ash` for it); this makes
  `gpu_available()` honour that instead of panicking.
- **Alternatives considered:** `catch_unwind` (hides the cause); enabling the
  `metal` feature (compiles an unused backend — the compositor and the Qt RHI
  interop are Vulkan-specific, so Apple has no GPU path anyway).

## Risks / Trade-offs

- `Qt6::GuiPrivate` absent → configure fails where the old hack silently
  "worked" on Debian. Mitigation: the failure names the private package; CI is
  unaffected.
- Offscreen `isNativeMenuBar()` may not reflect the cocoa platform → the check
  may need the manual fallback. Mitigation: the task explicitly allows it.
- Native bar ignores the CS6 menu-bar QSS on macOS → accepted; that is correct
  macOS behaviour.
- `frame_columns.cpp:154` offsets the workspace frame by `menuBar()->geometry()`,
  which is meaningless with a native bar. If the macOS run shows a bad offset,
  fix it under this change; otherwise leave it.

## Migration Plan

1. Apply the CMake change; confirm the Linux build still configures `GuiPrivate`.
2. Apply the temporary mac gate/paths; push; let the macOS job build this PR.
3. Add/execute the native-menu-bar check on the macOS run; iterate until green.
4. Revert the temporary gate/paths once `master` is green; record the revert.
5. Update `docs/dev/STATE.md`.
